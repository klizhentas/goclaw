# RFD 0000 - Core System Design (v1)

- Status: Active
- Authors: goclaw maintainers
- Created: 2026-02-25
- Updated: 2026-02-25
- Related:
  - `rfds/0001-task-scheduler.md` (scheduled task execution extension)

## Summary
Define the minimal, correct core architecture for goclaw:

1. Inbound chat messages are accepted (CLI-first).
2. Conversation and message history are persisted in SQLite.
3. One active worker per conversation is enforced.
4. Global concurrency cap applies across conversations.
5. OpenAI model integration returns assistant responses.
6. Assistant responses are persisted and routed outbound.

## Motivation
Ship a locally testable, deterministic core before adding integrations and advanced orchestration.

## Design Principles
1. Minimalism over feature breadth.
2. Correctness over cleverness.
3. Explicitness over abstraction.
4. Deterministic backend policy over model obedience.
5. Incremental evolution protected by tests.

## Goals
- Stable conversational interface with trigger semantics.
- Durable append-only conversation history.
- Predictable concurrency and locking behavior.
- Structured logs suitable for debugging and replay.

## Non-Goals (v1)
- Containers / sandbox runtime
- IPC bridges
- Multi-channel fanout
- Multi-provider abstraction layers
- Advanced permissions UX

## Interface Contract
1. Natural-language chat input (no rigid slash-command grammar).
2. Trigger prefix defaults to `@Andy` (configurable with `ASSISTANT_NAME`).
3. Non-main conversations require trigger by default.
4. Main conversation supports looser trigger policy and admin scope.
5. Backend enforces authorization and scoping rules.

## Core Architecture
Single process with modules:

1. `listener`
2. `store`
3. `dispatcher`/worker coordination
4. `model`
5. `outbound`

Message flow:
1. Receive inbound message.
2. Persist inbound.
3. Acquire conversation lock + global slot.
4. Build prompt from bounded history.
5. Call model.
6. Persist assistant response.
7. Emit outbound response.
8. Release lock/slot in `defer` paths.

## Concurrency Model
1. Per-conversation serialization via lock map.
2. Global semaphore caps active executions.
3. Store-first processing to support recovery.
4. Lock/semaphore release guaranteed on all paths.

## Storage Model
Minimum tables:
1. `conversations`
2. `messages`

Behavior:
1. Append-only message history.
2. Deterministic ordering (`created_at` + stable IDs).
3. Bounded history retrieval for prompt construction.

Note:
- Task scheduling tables and behavior are defined in `RFD 0001`.

## Model and Prompt
1. OpenAI integration is isolated under `internal/model`.
2. Request timeout is enforced by context.
3. Prompt builder uses fixed-size recent history window.
4. Oversized content is truncated safely.

## Logging
Use `log/slog` structured logs.

Minimum fields:
- `conversation_id`
- `message_id`
- `stage` (`ingress`, `persist_in`, `prompt_build`, `model_stream`, `persist_out`, `egress`)
- `duration_ms`
- `error` (on failure)

Rules:
1. One start and one completion/error event per stage.
2. No secrets in logs.

## Testing
Required local checks:
1. `make fmt`
2. `make test`
3. `make test-race`

Required behavior coverage:
1. DB operations and ordering.
2. Prompt window/truncation.
3. Trigger and role policy.
4. Per-conversation serialization.

## Disambiguation and RFD Precedence
1. `RFD 0000` is the baseline core design.
2. Feature-specific RFDs (e.g., `RFD 0001`) extend or constrain baseline behavior.
3. If two RFDs conflict, higher-numbered accepted RFD takes precedence for its scope.
4. Non-RFD docs are informational unless explicitly marked canonical.

## Rollout
1. Keep core path stable and test-backed.
2. Add extensions via focused RFDs.
3. Avoid broad rewrites without explicit acceptance criteria.
